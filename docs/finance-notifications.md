# Finance notification delivery

Customer payment/refund confirmations now use the independent Kafka consumer described in [customer-payment-emails.md](customer-payment-emails.md). Finance alerts retain the transactional path below; both audiences share the scoped, leased SMTP delivery engine.

Refund requests, independent approvals/rejections, confirmed refunds, provider-confirmed failure and release decisions enqueue email with the same PostgreSQL commit. New/reopened finance cases and release approval requests also enqueue. Triggers cover API, inbox and Lambda recovery writes. A failed email cannot approve a refund, mark money received or reverse stock.

Each merchant has an explicit `billing.notification_routes` destination. The default sender is disabled and there are no seeded production addresses. With no enabled route, a SUPPRESSED row records the decision; enabling a route affects future events. Recipient snapshots never silently redirect to a new address. The sender checks the active route again before SMTP. Revoking a route during an in-progress SMTP transaction cannot retract an email.

The worker claims one row in a short transaction with a 120-second token lease and increments its attempt count before sending. SMTP has bounded connect/read/write timeouts and runs after the claim commits. Expired claims can be recovered. Every completion/failure update matches the token, so an old process cannot overwrite a new owner. Up to eight uncertain attempts use exponential backoff; exhaustion becomes REVIEW, visible in Finance → Approval and refund emails. Sender disablement pauses existing pending work; disabling a route suppresses unsent work. Neither automatically backfills suppressed history.

SENT means SMTP acceptance only. Inbox receipt, spam placement, bounces and delivery ordering are not proven. A crash after SMTP accepts and before the database acknowledgement can duplicate the message. Retries retain the notification ID and Message-ID; recipient software may still show both. Messages include event time, refund transition version and operation references, and direct staff to sign in for current state. Email carries no approval token or one-click financial action. Maker/checker permissions remain server-side.

Enable with `BILLING_NOTIFICATIONS_ENABLED=true`. Configure `BILLING_NOTIFICATIONS_SMTP_HOST`, `_SMTP_PORT`, `_SMTP_USERNAME`, `_SMTP_PASSWORD`, `_FROM` and a trusted `BILLING_PUBLIC_URL`. Remote SMTP requires authenticated, mandatory STARTTLS with certificate/hostname verification. Store the SMTP password through private runtime configuration, never a tracked file or chat message. A local SMTP relay may be used without authentication. Production sender-domain SPF/DKIM/DMARC and bounce handling need the actual mail operator's setup.

Lab-only test routing requires non-production demo mode plus `BILLING_NOTIFICATIONS_TEST_MODE=true` and `_TEST_RECIPIENT`. Messages carry `[TEST]`. The isolated integration lab captures them in Mailpit on the laptop; those messages are not delivered to Gmail. Real inbox testing needs a configured authenticated mail transport. Test routing must never be deployed as Carrier production routing.

The laptop remains a shared availability dependency for PostgreSQL, sending, webhook ingestion and initial dispatch. A stopped laptop cannot send emails. AWS retains already-started Standard workflow state, but cannot recover against an unavailable laptop database forever; bounded exhaustion creates a finance case when the dispatcher can reconnect. Independent cloud failure alerts and off-host database/notification monitoring are production acceptance items, not demonstrated by this lab. Finite attempt exhaustion during a long SMTP outage currently needs staff review; there is no automatic circuit breaker or bounce receiver.
